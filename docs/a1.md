# A1 Always-on vs Serverless

2026-09-25

# 💼 The case

A climate research group has a script. You give it a date range and it
summarises daily rainfall across New South Wales for 10 climate models:
the mean, the wettest day, and the share of days over 10 mm.

Right now one person runs it on a laptop when someone asks. That works
until a colleague wants to call it from their own code, a dashboard
needs it on a schedule, and the laptop’s owner goes on leave.

|  | How it runs |
|----|----|
| Always-on, interactive | EC2 instance with JupyterHub or SSH access, interactive analysis |
| Always-on, as a service | The same EC2 instance, answering API requests |
| Serverless | Lambda function, called through API Gateway or triggered by an S3 event |

The first two are the same machine, running whether or not anyone is
using it. The code is similar in all three, but who triggers it and what
you pay for in between are very different.

## 1. Create your S3 bucket

`rubric={correctness:5}`

In the S3 console (find it using the search bar), choose **Create
bucket**, then:

- Name it `436c-a1-<your CWL>`, for example `436c-a1-jsmith`. Bucket
  names are unique across the whole of AWS, not just your account, which
  is what your CWL in the name is for.
- Region `ca-central-1`
- Leave **Block all public access** switched on. You won’t need public
  access, because the function will read the bucket using a role
  instead.
- Choose **Create bucket**.

Now open the bucket you just made and use **Create folder** twice, once
for `requests` and once for `results`. You’ll use these in Part 4. S3
has no real folders: what looks like a folder is a *prefix* on the
object’s name, which is why Part 4 asks you for a prefix of `requests/`
and not for a folder.

You should now see your bucket listed in `ca-central-1`, with the two
folders inside it and nothing else.

## 2. Set up your EC2 instance with JupyterHub

`rubric={correctness:10}`

### Create the instance role

**First, give the machine an identity.** The instance will read your
bucket, and it does that with a role, not with credentials typed into a
terminal.

- In IAM, choose **Roles → Create role**
- Trusted entity type: **AWS service**, use case: **EC2**, then **Next**
- Skip the permissions step with **Next**. The wizard only offers
  prebuilt policies here, and yours does not exist yet. You write it in
  a moment, after the role exists.
- Name the role `436c-a1-role` and choose **Create role**
- Open the role you just created, then **Add permissions → Create inline
  policy → JSON**, and paste this policy, substituting your bucket name.
  IAM denies everything it is not told to allow, so this policy is the
  only reason the instance can touch S3 at all. And it lists the exact
  actions on named buckets instead of granting everything, so the
  machine can do its job and nothing else.

``` json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::436c-a1-<your CWL>",
        "arn:aws:s3:::436c-a1-<your CWL>/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::436c-2026w1-public/a1/*"
    }
  ]
}
```

Choose **Next**, give the policy a name, and choose **Create policy**.
The role’s **Permissions** tab should now list the policy you just
wrote.

The two `Resource` lines are ARNs. An ARN (Amazon Resource Name) is
AWS’s full, globally unique address for one resource: the first line
names your bucket, the second names everything inside it, and those are
two different things.

Creating an EC2 role in the console also creates an *instance profile*
with the same name. An instance profile is the object EC2 attaches to an
instance in order to give it a role, and it is why `436c-a1-role` shows
up in the launch screen’s dropdown below.

### Launch the instance

In the EC2 console, choose **Instances → Launch instances**, then set:

- Region: `ca-central-1`
- Name: `436c-a1-<your CWL>`
- Amazon Machine Image (AMI): **Ubuntu Server 24.04 LTS (HVM), 64-bit
  x86**
- Instance type: `t3a.large`, which gives you 2 cores and 8 GB. The data
  needs about 400 MB in memory and you’ll have two things using it.
- Key pair: **Create new key pair**, name it `436c-ec2-<your CWL>`, type
  **ED25519**, format `.pem`, then **Create key pair**. The file
  downloads once, and you can’t download it a second time.
- Network settings: choose **Edit**, and under **Subnet** pick a public
  subnet, for example `cpsc436c-public-a`. Keep **Auto-assign public
  IP** enabled.
- Security group: two rules, each with **Source** set to **Anywhere**
  (`0.0.0.0/0`), so they keep working when you change networks:
  - SSH (port 22)
  - HTTP (port 80), which is JupyterHub
- Storage: 30 GB, `gp3`
- Under **Advanced details → IAM instance profile**, choose
  `436c-a1-role`
- Under **Advanced details → User data**, paste the script below,
  replacing the admin name with your CWL

``` bash
#!/bin/bash
curl -L https://tljh.jupyter.org/bootstrap.py \
  | sudo python3 - --admin <your CWL>
curl -LsSf https://astral.sh/uv/install.sh | UV_INSTALL_DIR=/usr/local/bin sh
```

The first command installs JupyterHub. The second installs `uv`, the
Python package installer you will use in step 3.

Choose **Launch instance**. The new instance appears in the
**Instances** list, with its status checks still running. Wait until the
instance shows 2/2 checks passed, then give it another 5 to 10 minutes.
The JupyterHub install is still running after the instance reports
ready.

Open `http://<your public IPv4 address>` in a browser. Use `http`, not
`https`. Log in with your CWL as the username, and set a password on
first login. Choose a real one: port 80 is open to the whole internet,
and this password is what stands between it and a shell on your
instance.

> [!NOTE]
>
> ### 💡 Why you never typed a password for S3
>
> When you run `aws s3 cp` on this machine in step 3, it will just work.
> No access key, no token, nothing pasted into a terminal. The machine
> carries a role, and AWS checks the role.
>
> That is the pattern for this whole course: **machines get roles,
> people get logins.** You will make the same move for the Lambda
> function in Part 4, where it is called an execution role. Anything
> that asks you to paste long-lived credentials into a file is showing
> you the wrong way.

## 3. Get the data into your bucket

`rubric={correctness:5}`

Open a terminal in JupyterHub (**File → New → Terminal**). Every command
in this step runs there, on the instance, not on your laptop.

First, in that JupyterHub terminal, install the libraries the rest of
the assignment needs, once, for everyone on the machine:

``` bash
sudo /usr/local/bin/uv pip install --python /opt/tljh/user/bin/python3 \
    awscli requests pandas pyarrow fastapi uvicorn boto3
```

`uv` is written with its full path because `sudo` in a JupyterHub
terminal does not look in `/usr/local/bin`. `--python` names the
environment to install into: the hub’s own Python, the one every
notebook on this machine runs. The install takes a few seconds.

In the JupyterHub terminal, copy the prepared data file
`rainfall_daily.parquet` from the course bucket into your own bucket,
then list your bucket to confirm it arrived:

``` bash
aws s3 cp s3://436c-2026w1-public/a1/rainfall_daily.parquet \
          s3://436c-a1-<your CWL>/rainfall_daily.parquet
aws s3 ls s3://436c-a1-<your CWL>/
```

You should see one object of about 99 MB. The file is Parquet: a
columnar file format that stores each column separately, which is why 10
million rows of rainfall fit in 99 MB. An `AccessDenied` here means the
instance profile from step 2 is not attached, or its policy names a
different bucket. The message says which action was refused on which
bucket: compare that bucket name, character by character, with the two
`Resource` lines in the role’s policy (**IAM → Roles → `436c-a1-role` →
Permissions**). Edit the policy in place. The running instance picks up
the change within seconds, so run the copy again.

**Only if that copy fails with `AccessDenied` and you cannot fix it**,
build `rainfall_daily.parquet` yourself instead. The course provides
`build_data.py`; upload it to the instance through JupyterHub, then, in
the JupyterHub terminal, run the script and copy the file it writes into
your bucket:

``` bash

python3 build_data.py --out rainfall_daily.parquet
aws s3 cp rainfall_daily.parquet s3://436c-a1-<your CWL>/rainfall_daily.parquet
```

Building `rainfall_daily.parquet` takes far longer than copying it, so
take this path only as a fallback. Either way you finish with one object
of about 99 MB in your own bucket.

In the JupyterHub terminal, copy the file onto the machine itself and
fetch `service.py`, the analysis code the rest of the assignment uses:

``` bash
sudo mkdir -p /srv/data && sudo chmod 777 /srv/data
aws s3 cp s3://436c-a1-<your CWL>/rainfall_daily.parquet /srv/data/
curl -o /srv/data/service.py https://436c-2026w1-public.s3.ca-central-1.amazonaws.com/a1/service.py
```

`/srv/data` should now hold `rainfall_daily.parquet` at about 99 MB and
`service.py` at a few kilobytes.

Then fetch the notebook you will work in, into your home directory
rather than `/srv/data`, so it shows up in the JupyterHub file browser:

``` bash
cd ~ && curl -O https://raw.githubusercontent.com/cpsc436c-2026w1/a1-starter/main/a1.ipynb
```

## 4. Run the analysis in JupyterHub

`rubric={correctness:10}`

In the JupyterHub file browser, open `a1.ipynb`, pick the Python 3
kernel, and run the first code cell. It holds this:

``` python
import sys; sys.path.insert(0, "/srv/data")
import os; os.environ["DATA_PATH"] = "/srv/data/rainfall_daily.parquet"
import socket, service

print("running on", socket.gethostname())
result = service.summarise("1990-01-01", "1999-12-31")
for row in result["models"]:
```

You should get 10 models. The driest is `MPI-ESM1-2-LR` at about 1.11 mm

your numbers differ, your copy of `rainfall_daily.parquet` is wrong: go
back to step 3, copy the object down again, and confirm `aws s3 ls`
reports about 99 MB before you re-run this cell.

The first line prints the EC2 instance’s hostname.

The first call to `summarise` prints a line like
`data loaded: 10,074,330 rows in ... ms`. Write that number down. You’ll
compare it against the Lambda’s load time in Part 4.

## 5. Run the same analysis over SSH

`rubric={correctness:10}`

Notebooks aren’t the only interactive mode. SSH (Secure Shell) opens a
terminal on the instance from your own machine. From your laptop
terminal, in the folder your browser saved the key into (usually
`~/Downloads`, so `cd` there first):

``` bash
chmod 400 <your-key>.pem
ssh -i <your-key>.pem ubuntu@<your public IPv4>
```

The first connection asks whether you want to continue connecting to a
host it has never seen. Type `yes`. You should land at a prompt reading
`ubuntu@ip-…:~$`. You are now typing on the instance, not on your
laptop.

If the connection hangs and then times out, port 22 is not open: on the
instance’s **Security** tab, the inbound rules should show SSH from
`0.0.0.0/0`. If it refuses immediately with
`Permissions 0644 … are too open`, the `chmod` did not run in the folder
holding the key.

Then, in that SSH shell on the instance. One new thing first: this shell
has its own `PATH`, and the hub’s environment is not on it, so point the
shell at the hub’s Python before you run anything:

``` bash
export PATH=/opt/tljh/user/bin:$PATH
cd /srv/data
DATA_PATH=/srv/data/rainfall_daily.parquet python3 -c \
  "import service, json; print(json.dumps(service.summarise('2000-01-01','2009-12-31'), indent=1))"
```

You’ll get the same 10 models with different numbers, because this is a
different decade.

Back in `a1.ipynb`, under **Step 5**, write one or two sentences
answering this: what did the machine have to be doing for either of
these two runs to work? This answer carries step 5’s marks, so put it in
that cell rather than in a scratch file.

# Part 3. Strategy: Always-on, as a service

⚙️ **Data engineering:** what has to be listening for a request to be
answered at all, and where the data sits between one request and the
next.

Same machine, same code. Now it answers other people’s requests instead
of yours.

## 6. Open a second port

`rubric={correctness:5}`

On your instance’s page in EC2, open the **Security** tab, click the
security group’s name, then choose **Edit inbound rules → Add rule**:

- Type **Custom TCP**, port **8000**, source **Anywhere-IPv4**

Choose **Save rules**. The inbound rules table should now have three
rows, for ports 22, 80 and 8000. TCP (Transmission Control Protocol) is
the protocol both HTTP and SSH run over, so **Custom TCP** here just
means a port you name yourself.

Port 80 is JupyterHub, and port 8000 will be the service. Both run at
once on the same machine, and you pay for the machine either way.

## 7. Run FastAPI and call it from your laptop

`rubric={correctness:10}`

In an SSH shell on the instance, opened the same way as in step 5:

``` bash
export PATH=/opt/tljh/user/bin:$PATH
cd /srv/data
DATA_PATH=/srv/data/rainfall_daily.parquet \
  nohup uvicorn service:app --host 0.0.0.0 --port 8000 > uvicorn.log 2>&1 &
sleep 15 && cat uvicorn.log
```

The `PATH` line appears again because this is a new shell, and every
shell starts with its own.

`nohup ... &` keeps `uvicorn` running after you disconnect, so the
service goes on answering requests once you close the SSH shell.

The log should show the data-load line, then
`Uvicorn running on http://0.0.0.0:8000`.

From your local device (laptop) in a new terminal window:

``` bash
curl "http://<your public IPv4>:8000/health"
curl "http://<your public IPv4>:8000/summary?start=1990-01-01&end=1999-12-31"
```

`/health` returns the row count and load time. `/summary` returns the
same 10 models you saw in Part 2.

> [!WARNING]
>
> ### ⚠️ If curl hangs instead of failing
>
> A request that hangs and then times out is the security group. Port
> 8000 isn’t open.
>
> A request that’s refused immediately means `uvicorn` isn’t running.
> Check `uvicorn.log`.
>
> The two failures look different, so read which one you got before
> changing anything.

# Part 4. Strategy: Serverless (event-driven)

⚙️ **Data engineering:** what has to happen on every call when nothing
is kept running between calls, where the data comes from each time, and
what that does to the time you measure.

The same analysis again, with nothing running in between.

Before you build it, find out what your account has spent so far. Your
account starts with no budget, and the Billing dashboard says *setup
required* until one exists, so create one, once: **Billing and Cost
Management → Budgets → Create a budget**, keep **Use a template
(simplified)**, choose **Monthly cost budget**, enter 10 USD and your
email, and choose **Create budget**. The template emails you as spending
approaches the amount, so a smaller amount, 5 to 7 USD, warns you
sooner. Open the budget and, under **Budget health → Current
vs. budgeted**, note the **Amount spent** line: what the account has
spent this month, a few cents on a fresh account. **Cost Explorer**, in
the same **Billing and Cost Management** menu, is enabled for the course
and shows the same spend split by service. Part 6 sends you back to the
budget, and you want to know what normal looks like before an endpoint
of yours is open on the internet.

## 8. Create the Lambda function

`rubric={correctness:10}`

In the Lambda console, choose **Functions → Create function**, then:

- Region: `ca-central-1`, checked in the top-right corner
- **Author from scratch**
- Function name: `436c-a1-<your CWL>`
- Runtime: **Python 3.14**, Architecture: **x86_64**
- Choose **Create function**. The function’s own page opens; everything
  below happens there.

The next two settings exist only once the function does, so set them
now:

- **Configuration → General configuration → Edit**, and set Memory to
  **2048 MB**. Lambda sells CPU in proportion to memory, and at 1,769 MB
  a function has one vCPU. This function uses about 1 GB while it runs,
  so 2048 MB covers it with room to spare. At the default 128 MB it
  fails.
- In the same panel, set Timeout to **15 seconds**, then **Save**. The
  default of 3 seconds is not enough to fetch 99 MB from S3: the first
  call takes about six seconds. Not 60 either: this function will sit
  behind an endpoint anyone can call, and a generous timeout on an open
  endpoint is room somebody else can use.

Then, on the same function page:

- Scroll to **Layers** at the bottom of the function page and choose
  **Add a layer → AWS layers**. Pick `AWSSDKPandas-Python314`, then the
  latest version, and choose **Add**. `pandas` is far too large to paste
  into the Lambda editor. A layer is a zip of libraries that Lambda
  unpacks alongside your code, and this one is published by AWS.

- Under **Configuration → Environment variables**, choose **Edit → Add
  environment variable**, add `DATA_URI` as the key, with
  `s3://436c-a1-<your CWL>/rainfall_daily.parquet` as the value, and
  choose **Save**. This is how the function finds your data. A test run
  that fails with `FileNotFoundError: rainfall_daily.parquet` means the
  function never saw this variable and went looking for the file next to
  its own code: check the key for typos, and that you pressed **Save**
  and the page reports the update succeeded.

### Give the function its execution role

Under **Configuration → Permissions**, click the role name. Lambda
created this role for you when you created the function, with just
enough permission to write its own logs to CloudWatch. It opens in IAM,
where you add the policy below the same way you did in step 2: **Add
permissions → Create inline policy → JSON**, substituting your bucket
name. This is the same move you made for [the instance
role](#instance-role), with a different name: an execution role.
Machines get roles.

``` json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::436c-a1-<your CWL>/*"
    }
  ]
}
```

You need the text of `service.py` in front of you on the laptop you are
browsing from. It is on the instance, at `/srv/data/service.py`. In
JupyterHub, open that file from the file browser, select all, and copy.

Back in the Lambda console, on the **Code** tab, replace everything in
`lambda_function.py` with what you copied, then press **Deploy**. Deploy
is what makes the new code live: until you press it, the editor runs the
old code while your unsaved changes sit on screen.

Test it from the **Test** tab with this event:

``` json
{ "queryStringParameters": { "start": "1990-01-01", "end": "1999-12-31" } }
```

Run it twice. Each run reports **Executing function: succeeded**; open
**Details** under that line for the duration, the billed duration and
the memory used. Look at the duration each time, and at `cold_start` in
the response.

> [!IMPORTANT]
>
> ### 👀 Quick check, the first run and the second run
>
> Both runs return the same JSON. The two reported durations will not be
> the same, and `cold_start` will not read the same on both.
>
> Write down both durations and both `cold_start` values next to the
> load time you recorded in Part 2. You now have three numbers for one
> analysis: what the instance paid to load the data, what the function’s
> first run cost, and what its second run cost. Which is which, and why,
> is yours to account for in Part 5.

## 9. Make it callable over HTTP with API Gateway

`rubric={correctness:8}`

On the function page, choose **Add trigger**, pick **API Gateway**,
then:

- **Intent**: Create a new API
- **API type**: HTTP API
- **Security**: Open
- Leave the rest at its defaults and choose **Add**

The trigger panel now shows an **API endpoint**. Copy the whole URL,
including the `/default/` stage and your function name on the end. It
looks like:

    https://abc123xyz.execute-api.ca-central-1.amazonaws.com/default/436c-a1-<your CWL>

From your laptop terminal, call it with the query appended:

``` bash
curl "https://abc123xyz.execute-api.ca-central-1.amazonaws.com/default/436c-a1-<your CWL>?start=1990-01-01&end=1999-12-31"
```

A `404 Not Found` almost always means part of the path is missing from
the URL you called. The `/default/` stage and the function name are both
part of it.

## 10. Make it fire on an S3 upload

`rubric={correctness:7}`

Not everything arrives as an HTTP request. Some work should start
because a file showed up.

On the function page, choose **Add trigger → S3**:

- Bucket: `436c-a1-<your CWL>`
- Event type: All object create events
- Prefix: `requests/`
- Suffix: `.json`
- Acknowledge the recursive-invocation warning

The prefix matters. Without it, the function’s own output written to
`results/` triggers the function again, which writes another output, and
so on. Setting the prefix is what stops that.

The function page’s diagram should now show both triggers, API Gateway
and S3.

In `a1.ipynb`, under **Step 10**, the next cell drops in a request file.
Put your own bucket name in it, then run it:

``` python
import boto3, json
BUCKET = "436c-a1-<your CWL>"
boto3.client("s3").put_object(
    Bucket=BUCKET, Key="requests/q1.json",
    Body=json.dumps({"start": "2005-01-01", "end": "2014-12-31"}))
```

Run the cell after it. It waits half a minute for the trigger, then
reads the result:

``` python
import time
time.sleep(30)
print(boto3.client("s3").get_object(Bucket=BUCKET, Key="results/q1.json")["Body"].read()[:300])
```

You should see the start of the same JSON you have seen three times now.
A `NoSuchKey` error means the result is not there yet, or the function
did not run. Wait another 30 seconds and run the cell again. If it is
still missing, read the function’s log: **Lambda → your function →
Monitor → View CloudWatch logs**, then open the newest log stream. No
log stream at all since you uploaded the file means the trigger never
fired. Check that the prefix is `requests/` with the slash and the
suffix is `.json`, then upload the file again: a trigger takes a minute
or two to start listening, and it misses anything that arrives before it
does. A log stream ending in an error means it fired and failed, and the
last line names what went wrong.
